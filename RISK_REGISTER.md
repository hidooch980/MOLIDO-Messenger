# Risk Register

| # | Risk | Impact | Mitigation / Status |
|---|---|---|---|
| 1 | PostgreSQL and Redis only verified on local dev instances | No deployed environment has a real, provisioned database or cache yet | PHASE 1 added Postgres schema/migration/auth; PHASE 3 added Redis-backed presence. Production/staging provisioning for both still open. |
| 2 | `validate-locales.js` doesn't detect duplicate JSON keys pre-parse | A duplicate key could silently drop a translation (last write wins under `JSON.parse`) | Add a pre-parse duplicate-key scan in a follow-up. |
| 3 | No automated RTL/LTR visual regression testing | A layout regression in a non-default direction could ship unnoticed | Manual test matrix documented in `TRANSLATION_TESTING.md`; automate later (e.g. Playwright + screenshot diff per locale). |
| 4 | ~~No WebRTC integration~~ — **PARTIALLY FIXED (PHASE 6)** | 1:1 voice/video calls now work (verified live with real media negotiation); multi-party rooms (the fuller Paltalk-style requirement) still need an SFU | 1:1 calls shipped in PHASE 6 (`src/call/CallContext.tsx` + backend signaling relay). Multi-party group calls remain explicit future work — mediasoup planned in `ARCHITECTURE.md`, not started. |
| 5 | Only fa/en have translated content; ar/ur/bal/tr/de/nl/fr/es are registry-only | Expanding language coverage requires real translation work, not just code | Registry/namespace structure already supports it without redesign (spec section 42's core requirement). |
| 6 | No confusable-username protection (spec section 23) | Cross-script lookalike usernames could enable impersonation | Not designed yet; needed before public registration ships. |
| 7 | No email/push delivery pipeline for localized notifications | `notifications.json` keys exist but nothing sends a real email/push yet | Deferred to a phase that adds an email/push provider. |
| 8 | Revenue flag not wired | Spec requires `REVENUE_ENABLED=false` as the enforced default | `revenue.json` namespace exists; the flag and gating logic don't yet — add before any billing UI work starts. |
| 9 | CI workflow untested on GitHub Actions | `.github/workflows/ci.yml` has only been exercised locally in this session | Verify on first push/PR. |
| 10 | No refresh-token/session-revocation | A leaked 7-day JWT cannot be invalidated before it expires | Acceptable for PHASE 1 development; must be closed before any production auth exposure. |
| 11 | Registration restricts usernames to ASCII alphanumeric/underscore | Sidesteps rather than solves spec section 23 (cross-script confusable usernames); also blocks legitimate non-Latin usernames | Needs a deliberate Unicode-username design (normalization + confusable-skeleton check) before loosening the current restriction. |
| 12 | System join/leave events aren't pushed live over the socket | A connected client only learns "X joined/left" on its next history fetch, not in real time | Deliberate PHASE 2 scope cut. Redis now exists (PHASE 3) but pub/sub across instances isn't wired yet — revisit once it is, so any backend instance can broadcast it. |
| 13 | No message edit/delete endpoints | Schema (`editedAt`/`deletedAt`) and translation keys (`chat.system.MESSAGE_EDITED/DELETED`) exist, but nothing lets a user actually edit or delete a message | Add routes + socket events in a follow-up phase; straightforward given the existing membership/ownership checks in `rooms/service.ts`. |
| 14 | Socket.IO server has one `io.use()` auth check but no per-message rate limiting | A malicious/buggy client could flood `chat:message` | Add rate limiting (e.g. a token bucket per user) before any public exposure. |
| 15 | No invite mechanism for private rooms | A private room (`isPublic: false`) can only gain members via direct DB/owner action today — there's no invite link, code, or "add user" endpoint | Needed before private rooms are usable by real users; candidate PHASE 3 work. |
| 16 | Room categories are a fixed compile-time list (`ROOM_CATEGORIES`) | Adding/renaming a category requires a code change + deploy, not an admin action | Acceptable for PHASE 2's scope; revisit if/when an admin panel exists. |
| 17 | Presence only broadcasts within a single backend process | `io.on("connection")`'s broadcast loop only reaches sockets connected to *this* process; a second instance behind a load balancer wouldn't see another instance's presence changes | Needs Redis pub/sub (or the Socket.IO Redis adapter) before horizontal scaling — tracked as a PHASE 4 candidate. |
| 18 | No rate limit on `friend:nudge` or `presence:set` | A client could spam nudges or flap presence state | Add per-user rate limiting alongside the `chat:message` one noted in risk 14. |
| 19 | `PATCH /api/me` accepts any HTTPS URL as `avatarUrl` with no upload/validation beyond `.url()` | A malicious URL (tracking pixel, non-image content, extremely large image) could be set as an avatar | Needs real image upload + validation (size/type/content) before any public exposure; out of scope until file storage is decided. |
| 20 | ~~Frontend pluralization keys used a dot suffix (`key.one`/`key.other`) that i18next didn't recognize by default (its separator defaults to `_`)~~ — **FIXED** | Building the rooms lobby's `t("member_count", { count })` actually triggered this (not merely theoretical): it rendered the literal string `"member_count"` instead of `"1 عضو"`/`"1 member"`, caught by a real browser check, not assumed from reading the code | Fixed by setting i18next's `pluralSeparator: "."` in `apps/frontend/src/i18n/index.ts` (alongside the earlier `{var}` interpolation fix) so both consumers of the same JSON files — the backend's own `Translator` and i18next — agree on one plural-key convention. Re-verified live afterward: the lobby correctly showed `"1 عضو"`. |
| 21 | ~~`ChatRoom` rendered a raw server error code directly to the user instead of translating it~~ — **FIXED** | A user would see `"GROUP_FORBIDDEN"` on screen instead of a real sentence in their language — the exact anti-pattern the error-code architecture exists to prevent | Fixed in the same pass as risk 20; `RoomsPanel`'s create/join actions, which had no error handling at all, got the same treatment. |
| 22 | No TURN server — calls rely on STUN only (`stun:stun.l.google.com:19302`) | Two peers behind symmetric NATs or restrictive corporate/mobile-carrier firewalls may fail to connect a call even though signaling succeeds | Verified working for the tested topology (two browser contexts, open networking); add a TURN server (self-hosted coturn or a managed provider) before relying on calls working for arbitrary real-world network pairs. |
| 23 | No rate limit on call signaling (`call:invite`, etc.) | A malicious/buggy client could spam call invites | Add per-user rate limiting alongside the `chat:message`/nudge ones noted in risks 14/18. |
| 24 | No "busy" UX beyond silently auto-declining a second incoming call | A caller whose target is already on another call gets no explanation — the call simply never connects, indistinguishable from a network failure from their side | Needs a dedicated `call:busy` signal back to the caller instead of a bare decline. |
| 25 | Calls have no server-side record (no call history, no missed-call notification) | A user who misses a call while offline/away has no way to know it happened | Would need a `Call` model (or reusing `Message`'s system-event pattern) plus notification delivery, which itself depends on risk 7 (no email/push pipeline yet). |
| 26 | ~~`RoomsPanel`'s chat-list preview showed the "no rooms exist" string for a room with no messages yet~~ — **FIXED (PHASE 7)** | A real room with zero messages displayed a wrong/confusing status ("no rooms exist yet") instead of "no messages yet" — found reviewing a live PHASE 7 screenshot, not by code review alone | Added a dedicated `groups.no_messages_yet` key (fa+en), fixed the fallback in `RoomsPanel.tsx`; re-verified live. |
